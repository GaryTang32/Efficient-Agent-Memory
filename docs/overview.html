Research brief · November 2026

Efficient Agent Memory

What this repository studies, how each memory and token-saving method works, and how well each one works today on four long agent tasks, measured on Claude Haiku and Sonnet.

≈ 2,100 benchmark runs26 methods and variantsClaude Code CLI routeEvidence to 5 Nov 2026

Key points
  • The objective is the fewest tokens and dollars per solved task, at full accuracy, with a slim working context, for long-running agents such as coding agents.
  • Fewer tokens is not fewer dollars. Re-sent history is cheap only while it stays byte-identical in the prompt cache; methods that edit history every step often cost more than they save.
  • Automatic beats model-managed. Steps the harness applies by itself (previews at ingestion, recall, compaction at a fixed trigger) work on both models; methods that need the model to manage its own memory fail on the weaker one.
  • AutoMemory v2 is the current best: Haiku 0.88 mean score at 85% of the unoptimised cost; Sonnet 0.98 at 64%. No newer method beats it across the board.

Recommendation: use automem_v2 as the default memory layer, with a cheaper model writing summaries for a strong agent. Validate it on real repositories next (4.5).

Glossary
Context window
The most tokens one request may hold. The tasks emulate a small window (16K–48K) to create memory pressure.
Prompt cache
Re-sent prefix tokens billed at 0.05–0.1× the input price, while the prefix is unchanged. Changing earlier history re-bills from that point as cache writes (2× on the Claude Code CLI, 1.25× on Bedrock).
Compaction
Replacing part of the history with a summary when the context grows too large.
Ingestion
The moment a tool result enters the history. Shrinking it here never invalidates the cache.
Session
One conversation. Multi-session tasks start each session fresh; only the memory method's own store carries over.
Floor / ceiling
The same model with no memory method in the task's window, and with its own large window. Every result is placed between them.
Recovery
The share of the floor-to-ceiling gap a method closes. 1.0 = as good as the ceiling.
Solved
A run in which every session's answer was fully correct.

Part 1 · Why

Objective and scope

Repository: Efficient-Agent-Memorydocs/problem_statement.md

1.1Executive summary

Objective
Save tokens and cost with a slim, effective context, without losing task accuracy, for long-running LLM agents.
Approach
Implement published memory and context methods faithfully (official code or prompts where they exist), measure each on the same long tasks and models, then combine the winners into one memory layer (AutoMemory).
Route
Claude Code CLI (Haiku, Sonnet; Opus in phase 1), with Bedrock-ready code paths. Bedrock validation is blocked on credentials.
Deliverables
A benchmark harness, 18 method implementations, AutoMemory v1/v2 as a bench technique, a Python library and an MCP server, and result reports for every phase.
Bottom line
AutoMemory v2 matches the unoptimised ceiling's accuracy on both models at 64–85% of its cost.

1.2The problem: two problems, one budget

A coding agent has no memory of its own. On every step the harness sends the whole conversation again. That makes the context window the agent's working memory, and makes cost grow faster than the work.

N − 1earlier steps re-sent on step N
0.05–0.1×price of a cached re-sent token
2×price of re-writing history on the CLI (1.25× on Bedrock)
+1%cost change of a "60–90% fewer tokens" shell tool in an independent test
Within a session: context
  • What should this request contain?
  • How small can it be without losing what matters?
  • Called context engineering, compaction, token optimisation.
Across sessions: memory
  • What should survive until the next session?
  • How does it come back at the right moment?
  • Called agent memory, long-term memory.

Measurecost per solved task at full accuracy, with real cache prices. Tokens removed is the wrong target.

1.4Scope

In scope
  • Within-session context methods: compaction, masking, folding, offload, deduplication, cache-aware batching.
  • Cross-session memory: note workspaces, official memory systems (MemoryOS, LightMem, Nemori), raw-history retrieval.
  • Faithful ports: official code, prompts and defaults; every deviation documented in its module.
  • Model-normalised evaluation on Haiku and Sonnet; cost with real cache prices.
  • Shipping the result: bench technique, library, MCP server.
Out of scope or not yet done
  • Self-hosted models and KV-cache editing (the user runs on hosted APIs).
  • Training-based methods (CORAL's RL variant, MemAgent's RL weights).
  • Bedrock validation: code ready, blocked on credentials.
  • Real-repository benchmark (SWE-bench Verified): designed, blocked on a permission.
  • Codex / OpenAI pricing: not yet re-priced.

1.5How effectiveness is measured

A stronger model scores higher with any method, so each method is measured against the same model's two anchors on the same task instances.

Score
Task accuracy in [0, 1], exact-match checks per session; a regression halves the repo_debug score.
Recovery
(score − floor) ÷ (ceiling − floor); defined when the ceiling beats the floor by at least 0.15.
Cost
Median USD per run as reported by the route, as a percentage of the ceiling's median cost.
Tokens
Prompt tokens (cached + uncached + written) and peak context per run.
Effort
Agent rounds, tool calls, wall-clock minutes, side-call cost (summaries, judges, memory systems).
Verdict
Model-robust = recovery ≥ 0.5 on both models; model-dependent = one model only; not effective = neither.

2.1The agent loop and its hooks

One minimal ReAct loop runs every method. A technique is a set of optional hooks, so the only difference between two runs is the technique under test. Combinations are pipelines of techniques.

  • Same rules for every method: an emulated context window (a request over it ends the session as an overflow), a context gauge in the newest message, at most 2 nudges after a malformed reply, a per-step output budget with recoverable offload.
  • Routes: Claude Code CLI (claude -p, stream-json, text tool protocol), Bedrock Converse, LiteLLM, Bedrock OpenAI-compatible endpoints, and a mock backend for offline tests.
  • Tests: 209 offline tests, including a mock run of every method on every long task.

2.4Logging and analysis

Per call

Tag (main, aux:summary, judge, probe), uncached / cache-read / cache-write / output tokens, latency, reported cost.

Per run

Score per session, success, steps, tool calls, peak context, cache-hit rate, cost by tag, wall time, overflow, history rewrites.

Per method

Records: ReFold labels and folds, SJC verdicts per entry, SelfCompact probe answers, CADOC commits, CORAL tool use.

Events

Compactions, offloads, previews, drops, nudges, retries, overflows, with the step they happened at.

Transcripts

Opt-in (EAM_TRANSCRIPTS): every message and call of every session, for failure analysis.

Analysis

analyze --summary --robust --metrics --reprice; medians (costs are heavy-tailed); superseded errors dropped; Bedrock re-pricing.

2.5Harness corrections that changed conclusions

Measurement bugs were found by checking surprising results against the raw usage. Affected rows were moved aside and rerun; the reports carry errata.

BugEffectFix
Retried CLI callsA retry summed both attempts' prompt tokens into the context size: false overflows.Billing keeps the sum; size checks use the final attempt.
Internal continuation turnsReplies over the output cap were continued internally; a 2.6K request read as 12.9K.32K cap; size = (prompt − output) ÷ turns. Every Haiku cell rerun.

ReSum
Alibaba Tongyi LabarXiv 2509.13313 · official WebResummer code (MIT)
acts at: Compactiondriven by: Harness
Idea
Periodic summarisation that replaces the whole history with one reset message.
Mechanism
  1. The harness watches the context size. When it reaches 0.9 × (K·1024 − 1000) tokens, it calls a summariser model.
  2. The summariser sees the question, the previous summary and every message since the last reset, and writes a <summary> of the essential facts. Its prompt forbids guessing or inferring.
  3. The history is replaced by one user message: the question plus the summary. The agent continues from there.
In this repo
Official prompts and trigger (third_party/resum.py). K is set per task so the trigger sits just under the window. Inside AutoMemory the summariser can be a cheaper model.
Evidence
Measured · both modelsMeasured on all four long tasks and both models; core of AutoMemory.

Observation masking
Lindenbauer et al. (NeurIPS'25 DL4Code)settings from AgentDiet / AttnCompress artifacts
acts at: History editdriven by: Harness
Idea
Old tool outputs are replaced by a placeholder; the agent keeps its own reasoning and calls.

  3. Nothing is summarised; the text is simply gone. Every masking edit changes earlier history, which breaks the prompt cache from that point on.

Window 2, minimum 300 tokens, the artifact's placeholder string. Publishes a stable boundary so a Bedrock cache point can sit before the edits.

AgentDiet
PKU + ByteDance (FSE'26)official artifact, CC BY 4.0 · prompt + Algorithm 1
acts at: History editdriven by: Side model
Idea
A cheap reflection model rewrites an earlier step to remove useless, redundant or expired content.
Mechanism
  1. Two steps after a step completes (a = 2), a reflection model reads it with one step of context either side (b = 1).
  2. If the step is longer than θ = 500 tokens, the model returns a trimmed version that drops what is no longer needed.
  3. The trimmed text replaces the original in the history.
In this repo
Official prompt and parameters verbatim; the reflector is the run's auxiliary model.
Evidence
Measured · mixedchain_hunt: Haiku 5/5 solved, but 410% of full-context cost with 7% cache hits. Sonnet's API safeguards refused the reflection calls on ledger_audit.

Official memory systems
MemoryOS (BUPT + Tencent) · LightMem (ZJU) · Nemori (Fudan + Shanda)official packages through a sidecar process
acts at: Cross-sessiondriven by: Side model
Idea
Dedicated long-term memory systems: tiers and heat-based promotion (MemoryOS), pre-compressed topic segments (LightMem), predictive episodes (Nemori).
Mechanism
  1. Each session's messages are added to the memory system, which extracts and stores memories with its own LLM calls.
  2. At the start of the next session the task is the query; retrieved memories go into the first message.
  3. Within a session, ReSum compaction is the same as in the comparator, so the memory system is the only difference.
In this repo
Separate virtualenv and sidecar (scripts/memory_sidecar.py); their LLM calls go through a private gateway and are billed as side calls. Runtime fixes are documented in docs/official_memory_repos.md.

CADOC
SJTUarXiv 2609.37012 · no public code: re-implemented from the paper
acts at: Render (cards)driven by: Harness
Idea
Large tool results become deterministic object cards, replaced in batches only when the cache economics say so.
Mechanism
  1. Each large tool result is registered as an immutable, versioned object; its bytes go to a store.
  2. Outside a hot tail (4 steps, 12,800 tokens) objects wait as pending. A ledger W accumulates the cost of carrying them raw.
  3. All pending objects are replaced by <OBJECT_CARD>s at once when W + w_r·G ≥ Q (Q = the cached tokens a rewrite would re-bill). retrieve_object returns exact bytes.
In this repo
Commit rule and defaults as published; rewrite priced as a cache write on this route (w_m = 2, w_r = 0.1 / 0.05).
Evidence

ReFold
UCSB + IntelarXiv 2610.07863 · official engine vendored (Apache-2.0)
acts at: Render (dedup + fold)driven by: Model + harness
Idea
The agent marks finished steps STALE; the harness folds them into one-line notes and stubs repeated reads, without editing history.
Mechanism
  1. Every reply starts with PROGRESS: and STALE: lines; only the last 3 steps can be named.
  2. Behind a boundary that advances 3 steps at a time, STALE runs fold into one note with their PROGRESS lines and file signatures.
  3. Repeated reads, searches and outputs become stubs pointing at the earlier copy; restore shows any original again.
In this repo
Official engine vendored; adapter for structured tools (restore is a tool). The loop now adds the context gauge to rendered copies.
Evidence

Mechanism
  1. The host (OpenClaw) writes a five-section summary: Decisions, Open TODOs, Constraints/Rules, Pending user asks, Exact identifiers.
  2. The summary is split into entries. A judge reads the compacted span with BM25-selected evidence (30K budget) and asks of each entry whether it came from an environment output.
  3. Entries scored below 0.5 are deleted; headings stay; any failure commits the raw summary.
In this repo
Judge = Claude Haiku returning p_yes per entry (the paper's Jev classifier is not available). Also adapted to ReSum's free-form summaries.
Evidence

Idea

4.4What works and what does not

Works on both models
  • Shrinking outputs at ingestion, with retrievalv2: Haiku 11/16 solved vs 7/16 at the same cost
  • Automatic recall and autosave of notesbeats MemoryOS, LightMem, Nemori by 0.2–0.5
  • Compaction at a fixed trigger, keeping recent stepswithout it: 0.04–0.62
  • A cheaper model writing the summariesSonnet: same accuracy, 20–40% cheaper
  • Batching any history editAKV: 93% → 22% cost at the same score
Fails or depends on the model
  • Editing history every stepmasking 608%, AgentDiet 410% of full-context cost on Haiku
  • Asking the model to manage its own memoryCORAL tools barely used; ReFold Haiku recovery 0.25
  • Fixed small preview thresholdsStrands research_corpus 0.11 / 0.72
  • Deleting old tool results over an APIAKV ledger_audit 0.00–0.17
  • Self-probing on the agent modelSelfCompact 138–179% mean cost

Let the harness do the remembering, and keep the cached prefix stable.

Shrink at the door

Decide what enters the history when it arrives; never rewrite it every step.

Reset rarely, keep the tail

One summary at 75% of the window, plus the last two steps and the notes.

Remember outside the context

Notes that come back by themselves beat engineered memory systems on agent work.

Conclusion

The repository set out to cut tokens and cost for long-running agents without losing accuracy. After faithful ports of 18 published and new methods and about 2,100 benchmark runs, the answer is a small set of automatic, cache-aware rules rather than any single clever technique: shrink outputs when they arrive, compact rarely and keep the recent steps, and keep notes outside the context that come back by themselves.

AutoMemory v2 packages those rules. It matches the unoptimised ceiling's accuracy on Haiku and Sonnet at 64–85% of its cost, and no method from the latest literature beats it across the board. The next proof point is real repositories.
