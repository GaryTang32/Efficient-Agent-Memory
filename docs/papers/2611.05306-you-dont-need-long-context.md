# You don't need long context (NVIDIA)

| | |
|---|---|
| arXiv | [2611.05306](https://arxiv.org/abs/2611.05306) (v1, 3 Nov 2026) |
| Authors | Belcak et al., **NVIDIA** |
| Harnesses | `mini-swe-agent` v2.4 (released harness, compaction added) and `mini-agent`, its generalisation to non-SWE tasks |
| Models | Claude Opus 4.5, GPT 5.6 Sol; open-weight (quantised): Qwen 3.6 27B, Qwen 3 Coder Next, Gemma 4 31B, Step 3.7 Flash, MiniMax M2.7 |
| Read | Full paper, 31 pages including appendices A–G (local copy, not committed) |

## Claim
Long context windows are not needed for agentic work. A short working context, kept small by **compaction** and
by **selective reading of long inputs**, matches or beats full-history agents, and is much cheaper to serve because
serving cost grows with context length (3.6–7× more per token at 256K than at 16K, by their cost model).

## Three regimes
| Regime | What the model sees | Role in the paper |
|---|---|---|
| **FHA** (full-history agent) | Everything so far | Baseline |
| **EoCC** (end-of-conversation compaction) | System prompt + task + a handoff recap. When the running context reaches the *compaction threshold*, the agent writes the recap itself and the conversation resets. The *total context limit* is never exceeded. | Main method; settings written "limit / threshold", e.g. 16K / 12K |
| **SAC** (single-action compaction) | Compacted state + one action at a time | Limit case; frames the agent as a *semantic state space model* (SSSM): the state is text, updated each step |

The threshold sits at 75% of the limit in most settings (48K/36K, 32K/24K, 16K/12K), the same trigger as our ReSum
compaction (0.75 × window).

## Compaction prompt (App. G)
The model writes the recap itself; the next conversation gets system prompt + task + recap. Fields of the
`mini-swe-agent` prompt:
1. **Objective**, one line.
2. **Established facts**: exact paths, relevant symbols or commands, observed values, important errors. Observations kept apart from unverified ideas.
3. **Applied changes**: each changed or created file, what changed, whether verified.
4. **Verification**: exact checks run, outcomes, failures, workarounds.
5. **Dead ends**: failed approaches that should not be repeated.
6. **Remaining plan**: outstanding subgoals in order, the **immediate next command or edit**, and the condition for completion.

Plus: "If needed output was truncated, give a narrow command to retrieve it." App. A lists the same ingredients as
what makes a compaction good: the task verbatim, the current occupation and next step, a decomposed plan and
requirements, and pointers to artifacts instead of their content.

## Selective reading (App. E)
Long inputs are files, not prompt text. Tools: `grep`, `sed`/`head`/`tail`, and `doc-read` (bounded window, default
6,000 characters, hard cap 8,000, and a header naming the command for the next window), `doc-stats`, `docs-list`,
`doc-syn` (synonyms for search). System prompt: "read only what you need … Do NOT try to dump the whole document."

## Results
**Long-horizon tasks** (App. C; accuracy baseline → EoCC at 16K / 12K):

| Benchmark | Opus 4.5 | GPT 5.6 Sol |
|---|---|---|
| SWE-bench Verified | 70.0 → 68.8 (best 73.6 at 48K/36K) | 84.4 → 84.6 (best 88.8) |
| SWE-bench Multilingual | 66.3 → 64.3 | 79.3 → 77.7 |
| Terminal-Bench 2.1 | 47.2 → 48.3 (best 52.8) | 87.6 → 85.4 |
| FRAMES | 81.0 → 79.6 | 90.2 → 87.1 |
| BFCLv3 long multi-turn (12K / 8K) | 62.0 → 62.5 | 39.5 → 39.5 |
| τ²-bench (8K / 6K) | 79.3 → 78.8 | 73.9 → 73.9 |

Compactions per task stay low: at 16K/12K on SWE-bench Verified the median is 1 (Opus) and 2 (GPT), the mean 2–3.

**Long-input tasks** (App. F; full input pasted → selective reading + EoCC):

| Benchmark | Opus 4.5 | GPT 5.6 Sol | Nominal cost, Opus |
|---|---|---|---|
| LongBench v2 | 68.0 → 67.6 | 70.8 → 72.6 | $275 → $185 |
| LOONG (avg) | 70.1 → 79.3 | 79.3 → 82.7 | $1,368 → $502 |
| AA-LCR | 65.0 → 84.0 | 82.0 → 83.0 | $52 → $27 |
| NIAH | 60.0 → 100 | 80.0 → 100 | $74 → $4 |
| RULER (recall) | 62.5 → 95.7 | 65.5 → 96.4 | $880 → $103 |
| BABILong | 67.1 → 92.0 | 70.7 → 94.0 | $361 → $57 |

Most long-input tasks finish with no compaction at all: selective reading does nearly all the work.

**Open-weight models** (App. D): robustness varies. Qwen 3.6 27B and MiniMax M2.7 hold up; Qwen 3 Coder Next
collapses on SWE-bench Verified at 16K/12K (53.0 → 3.6) because its verbose trajectories leave too little room
between compactions.

## The cost model, and what it means at list prices
The headline savings (2.2–8.8× for EoCC, 4.4–233× for long inputs) use an **"estimated optimized retail cost"**
(App. B): list prices multiplied by a context-length factor, modelling a provider that charges what long context
actually costs to serve. The tables also report **nominal retail cost** at today's flat list prices, with prompt
caching. On that basis:

| Benchmark | Opus 4.5, nominal | GPT 5.6 Sol, nominal |
|---|---|---|
| SWE-bench Verified | $420 → $313–380 (cheaper) | $168 → $184–203 (**10–21% dearer**) |
| SWE-bench Multilingual | $327 → $185–259 | $88 → $99–124 (**13–41% dearer**) |
| Terminal-Bench 2.1 | $88 → $90–115 (**dearer**) | $49 → $47–61 |
| FRAMES | $508 → $302–370 | $207 → $249–272 (**20–31% dearer**) |
| τ²-bench | $80 → $74–83 | $50 → $64–67 (**28–35% dearer**) |

The reason is in the token columns: the full-history baselines are mostly cache hits (SWE-bench Verified, GPT:
16.4M new vs 100.2M cached input), and every reset re-sends the recap as new input and breaks the cache. This is
the same effect this repository measures ("fewer tokens is not fewer dollars", README finding 1). Long-input
selective reading is cheaper on both bases, because it never puts the long input into the prompt at all.

## Relation to this repository
**Agrees with our measurements:**
- **Short contexts suffice for coding issues.** Our SWE-bench workdays peak at 12–26K tokens per session at the
  model's own window. `automem_v2_lean` at an emulated 16K window resolves 36/40 on Sonnet (ceiling 37/40) and 35/40
  on Haiku (= ceiling); they lose 1.2 points on Opus at 16K/12K.
- **Selective reading is the big lever for long inputs.** It is what our ingest previews (head/tail + stash +
  `retrieve_context`) and bounded tools (`read_file` 200 lines, `grep` 150 hits) do. Their pointer to the next window
  is a detail we do not yet print.
- **Harness-driven compaction with a fixed trigger works**, at the same 75% threshold.
- **Weaker models degrade first under a tight budget** (their open-weight results; our Haiku vs Sonnet results).

**Differs:**
- **Cost basis.** Our costs are list prices with prompt caching, which is how Bedrock and the Claude Code CLI bill
  below their long-context tiers. Under that billing their own nominal numbers show compaction often costing more,
  as ours do. Their large savings need context-length-dependent pricing, or self-hosted serving where KV-cache memory
  is the cost.
- **Who writes the recap.** Their agent writes its own recap with the same model. Our ReSum runs on a cheaper
  summariser (Haiku for Sonnet), and keeps the last two steps verbatim rather than resetting to recap only.
- **SAC** (compacting after every action) rewrites the prompt each step. With prompt caching this is the pattern that
  cost most in our tests (AKV rolling drop: 93% of the ceiling when dropping every turn, 22% in blocks of 8). It is not
  a fit for cached list-price billing.

## What to try here
1. **`compact=handoff`**: their six-field recap (objective, established facts, applied changes, verification, dead
   ends, remaining plan with the next command) as an AutoMemory compactor option, reset to system + task + recap.
   Variants: the recap written by the agent model (as in the paper) or by the summariser. Test on the SWE workdays at
   16K (`automem_v2_lean` with `compact=handoff`) and on the four synthetic tasks. Expected gain: "dead ends" and
   "applied changes, verified or not" are what a coding session needs after a reset and what a generic summary drops.
2. **Next-window pointers** in truncated tool output ("next: `read_file path 201-400`"), as `doc-read` prints. No API
   cost to build.
3. **Report cost on two bases** when it matters for a decision: list prices with caching (Bedrock/CLI today) and a
   context-length-priced estimate (self-hosting, or a provider that prices by length).
