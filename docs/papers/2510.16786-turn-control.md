## Problem
Every turn re-sends the whole history, so cost grows roughly quadratically with the number of turns;
agents also waste turns on unnecessary or harmful actions. Prior work optimises *each* turn
(compression, RAG, plan caching, multi-agent); nobody had studied controlling the *number* of turns.

## Method — three agent configurations
1. **Unlimited** (baseline): loop until the agent calls `task_done`.
2. **Fixed-turn + reminder**: hard limit `X`; after every tool result the harness appends
   `ENVIRONMENT REMINDER: You have X turns left to complete the task.` Task terminates at the limit.
3. **Dynamic-turn + reminder + growth** ("Dynamic X→Y"): start with limit X; if it is exhausted without a
   patch, grant a one-time buffer up to Y with
   `ENVIRONMENT REMINDER: You have used up all turns but have not yet completed the task. You are granted an additional X turns to continue and complete the task.`

Limits are **per-model percentiles of that model's own unlimited-run turn distribution** (25th / 50th / 75th):
Claude 4 Sonnet 44 / 52 / 63.75, Gemini 2.5 Pro 19 / 28.5 / 44.5, GPT-4.1 38.75 / 49.5 / 66.25.
Calibration therefore needs one baseline run.

## Setup
- 100-task SWE-bench Verified subset, stratified by repository.
- Tools: `str_replace_editor`, `bash`, `task_done`.
- Up to 3 attempts per task to produce a patch.
- Cost is computed from list prices **with prompt caching disabled** (§5.3, acknowledged as a threat to validity).
- One run per configuration; the two case studies were repeated 10×.

## Key results

**Unlimited baseline**

| Model | Solve | Turns | Input tok | Cost | $/solution |
|---|---|---|---|---|---|
| Claude 4 Sonnet | 75% | 5,704 | 186.0M | $585.21 | $7.80 |
| Gemini 2.5 Pro | 63% | 3,925 | 239.7M | $407.66 | $6.47 |
| GPT-4.1 | 62% | 5,641 | 159.1M | $322.02 | $5.19 |

**Fixed limit at the 75th percentile (the "sweet spot")**
- Claude 71% (−5.3% relative), cost −23.6%.
- Gemini 65% (+3.2%), cost −68.3%.
- GPT-4.1 57% (−8.1%), cost −38.4%.

**Tighter fixed limits**
- At the 25th percentile, Gemini's solve rate collapses (26%, a "threshold effect"). Claude and GPT-4.1 degrade gracefully.

**Reminders are essential.** If the baseline runs are simply truncated at the limit (no reminder), solve rates are far lower:
- 25th pct: Claude 24% vs 60% with reminders.
- 75th pct: Claude 63% vs 71% with reminders.

**Dynamic vs fixed**

| | Claude | Gemini | GPT-4.1 |
|---|---|---|---|
| **25→50 vs fixed 50**: solve | 64 vs 63 | 55 vs 52 | 57 vs 57 |
| **25→50 vs fixed 50**: cost | −15.6% | −6.0% | −24.3% |
| **50→75 vs fixed 75**: solve | 70 vs 71 | 64 vs 65 | 59 vs 57 |
| **50→75 vs fixed 75**: cost | −13.4% | −24.2% | −12.3% |

The abstract's "12–24% additional saving" holds for 50→75. For 25→50, Gemini's saving was only 6%.

**Case studies (10 repeats each; not significant at p<0.05)**
- 75th-pct limit vs unlimited: 8/10 vs 4/10 solved.
- Dynamic 50→75 vs fixed 75: 4/10 vs 2/10 solved.

## Limitations noted by the authors
- Single run per configuration.
- Proprietary models only.
- Prompt caching off.
- Results are tied to TRAE Agent and to the reminder wording.

## Relevance to a Bedrock API-only setup
- **Directly usable, training-free, model-agnostic.** It is a harness rule plus two reminder strings.
- **Cache-safe.** The reminder is appended after the newest tool result, so the cached prefix is untouched.
- **Open question this repo can answer:** the paper's savings were measured *without* prompt caching. With Bedrock caching (cache reads ≈ 0.1× input price), the quadratic input term is much cheaper, so the saving from fewer turns should shrink. By how much, and does the solve-rate effect ("moderate urgency helps") still hold? Measure both.
- **Composes with memory techniques.** Fewer turns means fewer re-sent prefixes, which is orthogonal to shrinking each turn.

## Implementation plan
- Port as a technique `TurnBudget(mode="fixed"|"dynamic", limit, extension)` using the exact reminder strings above.
- Add a calibration helper that sets limits from percentiles of a baseline run per model.
- Compare against our own runs of the paper's code only if we add a SWE-bench task: the official artifact is the TRAE-agent fork on Figshare.
