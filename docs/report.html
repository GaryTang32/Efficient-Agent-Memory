Work report · 12 November 2026

Efficient Agent Memory

What was built, what the measurements show after a validation round, how the memory layer ships as a Claude Code plugin, and what is left to do.

≈ 3,900 benchmark runs27 methods and variantsClaude Haiku and SonnetSWE-bench Verified: Django and SymPyPRs #1–#8 merged

Key points
  • Fewer tokens is not fewer dollars. Re-sent history is cheap while it stays in the prompt cache; methods that rewrite it every step cost more than they save (AKV: 93% of the ceiling's cost dropping every turn, 22% in blocks of 8).
  • Let the harness remember. Previews at ingestion, automatic recall and compaction at a fixed trigger worked on Haiku and Sonnet; methods that need the model to manage its memory failed on Haiku.
  • AutoMemory v2 matches the unoptimised ceiling on four long multi-session tasks at 85% (Haiku) and 58% (Sonnet) of its cost; a same-day re-run and a repeat gave 74–87% and 56%. No newer published method beats it across the board.
  • On real coding issues (Django and SymPy, SWE-bench Verified), automem_v2_lean inside a 16K window resolves as many issues as the unoptimised agent with its full window. On Sonnet it costs 80% of that agent over three runs (95% interval 72–90%); on Haiku its cost cannot be told apart from the ceiling's.
  • A validation round (same-day controls, repeats, a code audit, a second repository) confirmed both results and withdrew four smaller claims, among them "handoff costs more than ReSum". About a quarter of all measured cost was a harness artifact, now capped and counted.
  • A follow-up with three runs per cell settled three open questions: lean is cheaper than the ceiling on Sonnet and not on Haiku; the handoff recap and a ReSum summary are level; EoCC alone, without previews, resolves 5 fewer issues in 100.
  • Pilots inside Claude Code: on single issues (Haiku: 16/20 resolved with the plugin vs 16/20 without, at +5% cost; Sonnet: 16/20 resolved with the plugin vs 15/20 without, at -10% cost) and in 12-issue sessions with compaction (cost −4% Haiku, +1% Sonnet, ±1 issue), the plugin is neutral. Claude Code already caches, compacts and filters long output itself.

Recommendation: use the plugin's harness steps (previews, handoff at compaction, recall) rather than instructions in CLAUDE.md; pick automem_v2 for multi-session work and automem_v2_lean for coding issues. Expect the saving on the dearer model: with Sonnet, 44% on multi-session work and about 20% on coding issues (5–30% across the three issue sets).

1.2What was built

Benchmark harness

ReAct loop with technique hooks, emulated windows, a cache-aware cost meter; Claude Code CLI, Bedrock, LiteLLM and mock backends.

27 methods and variants

Faithful ports of published methods, each with its source and deviations documented, from ReSum to NVIDIA's EoCC.

Tasks

Four long synthetic tasks and SWE-bench Verified workdays on Django (100 issues, plus workdays of related issues) and SymPy (75), graded as SWE-bench grades them.

AutoMemory

The combined memory layer as a bench technique, a Python library and an MCP server, with six presets.

Claude Code plugin

plugins/automem: four hooks, a skill and a handoff command; standard library only.

Docs

README with charts and flowcharts, the interactive overview, paper notes, methodology, CONTRIBUTING and CITATION.

2.1Key findings

FindingEvidence
Fewer tokens is not fewer dollarsRewritten history is billed as cache writes (2× on the CLI, 1.25× on Bedrock). Masking cost up to 608% and AgentDiet 410% of full context on Haiku.
Automatic beats model-managedCORAL's memory tools were barely used (Haiku 7 of 56 sessions); ReFold's Haiku recovery was 0.25. Harness-applied previews, recall and compaction held on both models.
Plain notes beat memory systemsMemoryOS, LightMem and Nemori scored 0.2–0.5 lower than a note workspace with the same compaction.
Match the layer to the workNotes are essential for multi-session tasks (without them 0.64 and 0.87 in score at 1.5–2.5 times the ceiling's cost) and overhead on coding issues, even related ones (Haiku: twice the ceiling's cost, fewer issues resolved).
Real coding sessions fit in short contextsInside a 16K window with compaction, the agent resolves as many issues as with its full window, on Django and on SymPy. Sessions peak at 16–21K tokens without a limit.
The kind of summary matters little on coding workOver three runs on Django, NVIDIA's handoff recap and a ReSum summary resolved the same number of issues (80 and 81 of 100 on Haiku, 88 and 87 on Sonnet) at the same cost. Trimming at ingestion matters more: the recap alone, without previews, lost 5 issues in 100.
Measure the noise before rankingThe same setting run twice differed by up to 38% in cost; about a quarter of all measured cost was runaway replies at the output cap. Four early rankings did not survive a same-day re-run; three runs per cell were needed to establish the lean saving on Sonnet.
Grading must follow SWE-bench exactlyThe first 40-issue run checked 63% of the official tests (docstring-named tests were dropped); fixed and superseded.

2.2What works, what does not

Works on both models
  • Shrinking outputs when they arrive, with retrievalHaiku 11/16 runs solved vs 7/16
  • Automatic recall and autosave of notesbeats engineered memory systems by 0.2–0.5
  • Compaction at a fixed trigger, keeping recent stepswithout it: 0.04–0.62
  • A cheaper model writing summariesSonnet: same accuracy, 20–40% cheaper
Fails or depends on the model
  • Editing history every stepmasking 608%, AgentDiet 410%
  • Asking the model to manage its memoryCORAL tools barely used
  • A compaction method alone, without a guardEoCC alone: one session in five ran out of the 16K window; 5 fewer issues resolved than its same-day ceiling on both models (2 gained, 12 lost, p = 0.013)
  • Notes on coding issuesHaiku: 208% of the ceiling's cost on related issues, 6 fewer resolved
  • Ranking settings from one runcost differed by 7–38% between two runs of the same setting (1–15% since the 8K cap)

Part 4 · For everyday users

Claude Code plugin

plugins/automemclaude --plugin-dir plugins/automem

4.1How it works

The plugin runs the measured harness steps as Claude Code hooks: no extra model calls, nothing rewritten in the cached history. Claude Code already caches prompts and cuts long Bash output to a 2 KB head-only preview with the full text saved to a file; the plugin builds on that.

HookWhat it doesMeasured rule behind it
PostToolUse (Bash)Long output reaches the model as head + tail (1,500 characters each). For output Claude Code truncated, the tail is read from Claude Code's own saved copy, so test summaries and failures at the end stay visible.Previews at ingestion (Haiku 11/16 vs 7/16)
PreCompactCompaction keeps NVIDIA's six-field handoff recap.Level with a ReSum summary in accuracy and cost over three runs
SessionStartRecalls this project's notes at startup, resume, clear and after compaction.Recall: Haiku 0.34 without, 0.99 with notes on Sonnet
StopSaves each turn's final message as a project note.Autosave

Checked live: with a 108 KB output, plain Claude Code showed the model lines 1–234; with the plugin the model saw the head and the real last line, and found a middle line in the saved file without re-running the command.

Status as of 12 November 2026

5.1Blocked

Bedrock validation

Blocked: credentials —

Every result uses the Claude Code CLI's list prices. Bedrock bills cache writes at 1.25× (not 2×) and uses explicit cache points, which could change the cost ranking. Needs AWS credentials or a Bedrock API key; runbook in scripts/run_bedrock_validation.sh.

GPT and other non-Claude models

Blocked: credentials —

No non-Claude model has been measured. GPT-5.6 is reachable through Bedrock's OpenAI-compatible endpoints with the same key; prices go in config/models.json.

5.2Next steps

Native tool-calling route

Blocked: credentials —

The runaway replies come from emulating tools as text through the Claude Code CLI. A route with native tool calls (Bedrock Converse) removes them at the source and is the same work as the Bedrock validation above.

Three runs of the SymPy and related-issue sets

Next ≈ $45

Lean's cost against the ceiling is established on the 100 Django issues only. On SymPy and the related-issue workdays each cell ran once and the intervals are wide (Sonnet: 70% [54–109] and 95% [66–126]).

Three runs per cell on Django

Done: lean is cheaper on Sonnet $81 with the next two

Ceiling, lean and lean + handoff, three runs each. Sonnet: lean costs 80% of the ceiling [72–90] (82%, 77%, 81% run by run) and resolves 87 of 100 against 87. Haiku: 96% [83–110], 81 against 78. With the 8K cap, two runs of one cell differ by 1–15% in cost.

EoCC alone, corrected grading, next to its ceiling

Done: cheaper, fewer issues

Haiku 75 of 100 against 80 for the ceiling at 85% of its cost; Sonnet 85 against 90 at 74%. Pooled over both models it gained 2 issues and lost 12 (p = 0.013). 22 and 19 of 100 sessions filled the 16K window and were stopped; 8 of the 12 lost issues were in those sessions.

Handoff recap or ReSum summary

Done: level

Over three runs the two resolve the same number of issues (Haiku 80 and 81, Sonnet 88 and 87) at the same cost (handoff at 104% [93–118] and 102% [94–111] of ReSum). The earlier pooled 22 against 11 (p = 0.08) did not repeat: 10 against 12 in the two new runs.

Decide the plugin's role

Next no API cost

Both pilots (short and long sessions) found the plugin neutral in Claude Code, which already caches, compacts and filters output. Keep it as an optional, harmless add-on; aim further work at agents without these built-ins (custom loops on Bedrock, other CLIs).

Brief handoff recap

Done: no advantage $25

Six fields as terse bullets, at most 150 words. Its first reading (79% of the ceiling's cost on Haiku, the cheapest per resolved issue) did not repeat on the same day: 90% and the fewest issues resolved (75). Kept as the option handoff_variant=brief, without a claim.

Adaptive workspace

Done: an option, not the default $32

A short question to the summariser at each session start chooses notes on or off. On Sonnet it stayed close to the right fixed preset on both kinds of work (1.00 at 61% of the ceiling's cost on the synthetic tasks; 86 of 100 Django issues at 105%). On Haiku it cost more than the right preset on both (155% and 131%). Kept as automem_v2_adaptive.

Report cost on two price bases

Next no API cost

List prices with caching (Bedrock and the CLI today) and context-length pricing (the NVIDIA paper's model) for self-hosted or long-context-tier users.

5.3Known gaps

Two repositories, one language

Gap

The SWE-bench sets are Django and SymPy, both Python. Sonnet's out-of-sample sets are smaller (50 related issues, 40 SymPy issues).

One run for most cells

Gap

Only the ceiling, lean and lean + handoff cells on Django were run three times. For the other cells, intervals are a bootstrap over the workdays of one run and are wide; there is no correction for the number of comparisons.

Rows before 12 November

Gap

They ran with a 32K output cap and thinking settings inherited from the launching session, and do not record the CLI version. New rows record all three.

Emulated windows

Gap

The synthetic tasks emulate small windows (16K–48K) to create memory pressure.

Local-only reports

Gap

Detailed reports in docs/results/ and the rows behind docs/overview.html are git-ignored, so a fresh clone cannot rebuild those pages; the README charts can be rebuilt.
